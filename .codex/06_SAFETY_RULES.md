# 06 — Safety Rules

This file defines the deterministic rule-based safety engine.

## Core principle

The final safety result must be generated by backend rules, not by AI.

AI can help identify medication candidates or rewrite messages, but it must not decide whether the user can take medicine.

## Status values

```ts
type SafetyStatus = 'allowed' | 'warning' | 'blocked';
```

## Severity values

```ts
type SafetySeverity = 'info' | 'warning' | 'critical';
```

## Result shape

```ts
type SafetyCheckResult = {
  id?: string;
  status: 'allowed' | 'warning' | 'blocked';
  canConfirmIntake: boolean;
  reasons: SafetyReason[];
  suggestedAction: string;
};

type SafetyReason = {
  code: string;
  severity: 'info' | 'warning' | 'critical';
  message: string;
  metadata?: Record<string, unknown>;
};
```

## Aggregation rule

- If any reason has `severity = critical`, final status is `blocked`.
- Else if any reason has `severity = warning`, final status is `warning`.
- Else final status is `allowed`.

Confirmation behavior:

| Status | canConfirmIntake | Behavior |
| --- | --- | --- |
| allowed | true | User can confirm intake normally. |
| warning | true | User must explicitly acknowledge warning before confirm. |
| blocked | false | Do not allow direct intake confirmation. |

## MVP rules

### RULE 1 — Inactive medication

If `user_medications.is_active = false`, block.

```txt
code: MEDICATION_INACTIVE
severity: critical
message: Thuốc này đã được đánh dấu là ngừng sử dụng. Vui lòng kiểm tra lại trước khi uống.
```

### RULE 2 — Missing medication schedule

If no active schedule exists for the selected medication, warn.

```txt
code: SCHEDULE_NOT_FOUND
severity: warning
message: Thuốc này chưa có lịch uống trong hồ sơ của bạn. Vui lòng kiểm tra lại hướng dẫn sử dụng.
```

### RULE 3 — Not scheduled today / not in today's plan

If the medication is not part of today's active plan, warn.

For MVP, if schedules are daily by default, this can be equivalent to missing active schedule.

```txt
code: NOT_IN_TODAY_PLAN
severity: warning
message: Thuốc này không nằm trong kế hoạch uống thuốc hôm nay của bạn.
```

### RULE 4 — Too early compared to scheduled time

If the request includes `scheduledTime`, verify that the time exists in the selected schedule or active medication plan. If current time is earlier than the selected scheduled time by more than the allowed early window, warn. If it is later than the selected scheduled time by more than the allowed late window, warn.

Suggested default:

```txt
allowedEarlyMinutes = 30
allowedLateMinutes = 120
```

```txt
code: TOO_EARLY
severity: warning
message: Hiện tại có vẻ chưa đến giờ uống thuốc này.
```

```txt
code: DOSE_TIME_PASSED
severity: warning
message: Giờ uống thuốc theo lịch đã qua. Vui lòng kiểm tra lại trước khi xác nhận.
```

### RULE 5 — Too soon since last intake

If the user has taken this medication recently and `now - lastTakenAt < min_interval_hours`, block.

```txt
code: MIN_INTERVAL_NOT_REACHED
severity: critical
message: Bạn vừa uống thuốc này gần đây. Chưa đủ khoảng cách tối thiểu giữa hai lần uống.
```

If `min_interval_hours` is missing, do not block; add missing-data warning instead.

### RULE 6 — Daily dose count exceeded

If today's intake count for this medication is already greater than or equal to `times_per_day`, block.

```txt
code: DAILY_DOSE_LIMIT_REACHED
severity: critical
message: Hôm nay bạn đã uống đủ số lần theo lịch của thuốc này.
```

### RULE 7 — Allergy match

Compare saved allergies with:

- `user_medications.name`
- `user_medications.active_ingredient`

Use case-insensitive normalization.

If matched, block.

```txt
code: ALLERGY_MATCH
severity: critical
message: Thuốc hoặc hoạt chất này có thể liên quan đến dị ứng đã lưu trong hồ sơ của bạn.
```

### RULE 8 — Missing active ingredient

If active ingredient is missing, warn.

```txt
code: MISSING_ACTIVE_INGREDIENT
severity: warning
message: Thuốc này chưa có thông tin hoạt chất, nên hệ thống không thể kiểm tra dị ứng theo hoạt chất đầy đủ.
```

### RULE 9 — Missing health profile

If profile is missing conditions/allergies, warn.

```txt
code: INCOMPLETE_HEALTH_PROFILE
severity: warning
message: Hồ sơ sức khỏe của bạn chưa đầy đủ, cảnh báo có thể chưa chính xác.
```

## Suggested implementation

```ts
export function runSafetyRules(input: SafetyRuleInput): SafetyCheckResult {
  const reasons: SafetyReason[] = [];

  checkMedicationActive(input, reasons);
  checkScheduleExists(input, reasons);
  checkScheduleTime(input, reasons);
  checkMinimumInterval(input, reasons);
  checkDailyDoseLimit(input, reasons);
  checkAllergies(input, reasons);
  checkMissingData(input, reasons);

  const status = aggregateStatus(reasons);

  return {
    status,
    canConfirmIntake: status !== 'blocked',
    reasons,
    suggestedAction: buildSuggestedAction(status),
  };
}
```

## Duplicate confirmation protection

When user confirms intake, backend should check whether there is already an `intake_events` record for the same medication in a close time window.

Suggested window:

```txt
same medication + same profile + within 30 minutes
```

If duplicate is detected, reject or return warning.

## Message style

Messages must be:

- Short
- Vietnamese
- Easy to understand
- Not too technical
- Not medical advice beyond safety warning
- Not dependent on color only

## Important non-goals for MVP

Do not implement full drug interaction checking unless the team has a trusted dataset.

Do not implement contraindication checking against diseases unless there is a trusted source. For MVP, only simple allergy matching and schedule/intake safety rules are required.
